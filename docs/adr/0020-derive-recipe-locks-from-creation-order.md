# レシピ一覧の並びとFreeのロック判定を追加日に揃える

レシピ一覧は`updatedAt`の降順で返し、ProからFreeに戻ったユーザーのロックも`updatedAt`が新しい5件以外にかけていた。一覧に並び替えを加えるにあたり、既定の並びと期間見出しを追加日（`createdAt`）に変える。`updatedAt`が変わるのは作成と編集の保存だけで、閲覧や調理では変わらない。先月取り込んだRecipeの分量を1か所直すと「今週」の棚へ移り、写真の並びを位置で覚えている利用者はそれを見失う。期間見出しとして思い出す手がかりになるのも、保存した時期のほうである。

## ロック判定は既定の並びと同じ軸にする

並びを追加日にしてロックを`updatedAt`のまま残すと、既定の一覧でロック中のRecipeが途中に混ざる。Pro期間中に古いRecipeを編集していると、それが開けておく側に入り、より新しいRecipeがロックされるためである。利用者からはロックが無作為にかかっているように見え、どれがロックされるかを画面から予測できない。

そこでFreeで開けておくRecipeを、`createdAt`が新しい5件（同時刻は`id`の降順）にする。判定は引き続きDBに保存せず都度導出し、一覧と詳細は行を引くSQLに同じ判定（その5件に入るか）を列として埋め込む。判定はplanに依存しないのでplanの導出と同じ波で引け、Freeでも往復は増えない。Proでは使わない列になるが、別のクエリは増えない。

- 追加日のどちらの向きで並べても、検索で絞り込んでも、ロック中のRecipeは一続きになる。一覧は案内を一度だけ出せばよい。
- 編集してもロックは動かない。開いているRecipeを削除すると、境目のすぐ隣のRecipeが開く。
- 「新しく保存した5件」と一文で説明でき、追加日は期間見出しで見えている。

何度も作る古い定番のRecipeがロックされる弱点は残る。ただし`updatedAt`も調理を記録しないため、従来の判定でも守れていなかった。

## 採らなかった案

- **`updatedAt`が新しい5件のまま**：上記のとおり、既定の一覧でロックが混ざる。
- **`createdAt`が古い5件を開けておく**：「Freeで保存した分が残る」という公平さはあるが、既定の新しい順では先頭がロック中で埋まり、直近に保存したRecipeが開けない。
- **開けておく5件を利用者が選ぶ**：定番を守れるが、選択を永続化する必要があり、ロック状態を保存しない方針に反する。選ぶ画面も要る。ダウングレードしたときにしか起きないため、今は導出規則で足りる。

## 並びの選択肢は追加日の2つに絞る

並び順は`newest`（既定）と`oldest`だけにする。`updatedAt`の並びを入れるとその並びだけロックが混ざるうえ、利用者が求める「最近作った順」の代わりにもならない。名前順は、漢字混じりのタイトルがDBの照合順序では読み順にならないため入れない。

`updatedAt`で並べる読み取りがなくなるので、`recipes_user_id_updated_at_idx`を`recipes_user_id_created_at_idx`に置き換える。一覧のcursorは並び順を含み、別の並び順のcursorは`invalid_recipe_list_cursor`として拒否する。本番稼働前のため、既存のcursorやロック状態の移行は考えない。
