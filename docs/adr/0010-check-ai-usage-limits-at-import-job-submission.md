# AI月次利用上限をImport Job投稿時に判定する

ADR 0008は、ユーザーがFree上限に達した瞬間、つまり最もアップグレード意欲が高い瞬間に、英語のエラーコードか無反応だけを残してはならないという理由から、Shortcutへサーバー生成のnoticeを返す設計を採用した。しかしAI月次上限だけはこの原則の外に置かれていた。判定はキュー処理中の`consumeAiUsage`が初めて行うため、上限に達しているユーザーにもShortcutは「取り込みを開始しました」を返し、結果はPush通知でしか伝わらない。しかもADR 0009が決めたとおりPushの文言は`outcome`だけで決まり、失敗はすべて「レシピを取り込めませんでした」になる。理由は伝わらず、Push未許可のユーザーには何も届かない。

Push通知はbest-effortであり、Import Jobの状態を変えないというADR 0006の決定によって、通知の失敗も未許可も正常な状態である。理由の唯一の伝達経路をbest-effortの通知に置くことはできない。したがってAI上限の判定を投稿時へ引き上げ、その場で理由を返す。ShortcutとWebはADR 0006が定めた同じURL Import Job submission Moduleを共有しているため、この判定は両経路に同時に効く。

## 投稿時はチェックだけを行い、消費はキュー処理中に残す

投稿時に消費し失敗時に返却する予約制は採らない。AIが動いていない失敗で枠を焼かないための返却処理と、返却前にクラッシュした場合のリーク対策が必要になり、複雑さが利得に見合わない。投稿時は当月の利用回数を照合するだけとし、上限未満のときだけincrementする原子的なUPSERTはキュー処理中の`consumeAiUsage`に残す。

その結果、「上限-1回の状態で同時に2件投稿した」境界では1件の超過を許容する。この判定はフォールバックの追加ではなく、圧倒的多数である「すでに上限到達済み」のケースを同期側へ移すためのものである。境界で通り抜けた1件は、`ai_usage_limit_exceeded`で`failed`になる従来の非同期失敗経路がそのまま受け止める。すなわち上限超過の扱いは経路が増えるだけで、失われる保証はない。

判定は保存上限を見ている`createUrlJob`の単一SQLへ畳む。そこはプランを算出済みで、往復が増えず、プラン同期を二重に走らせずに済む。ADR 0001が単一SQLを推奨する理由はアトミック性の表現であり、この判定自体はアトミックである必要はないが、同じ投稿時ゲートを2つの機構に分ける利点はない。既存の「active Jobがあれば上限を評価しない」構造をそのまま使うため、優先順位は`existing_active_job`、保存上限、AI上限の順になり、既存の挙動が変わらない。

## プランで別のreasonに分ける

保存上限（free 5件）は投稿時にブロックされAIを消費しない。そのためfreeがAI枠（10回/月）へ到達するには、AIを消費したのに保存に至らない失敗が5回以上必要であり、例外的である。実際にAI上限へ到達するのは主にProユーザー（300回/月）であり、すでに払っている相手へ「Proにすると」と案内することに意味はない。

したがってfreeには`ai_usage_limit_exceeded`、proには`ai_usage_quota_exhausted`を返す。前者は課金画面への`openUrl`を持ち、後者は残された行動が待つことだけなのでopenUrlを持たず、リセット時期だけを伝える。リセットはJST月初固定であるため「毎月1日」は常に真であり、日付の補間は不要である。noticeカタログは静的なまま保てる。

reasonはADR 0008が定めたとおりHTTPステータスに代わる監視の軸でもある。free到達はコンバージョン機会であり通常の利用結果、pro到達は容量または濫用の兆候であり、運用上は別の事象である。この非対称性に合わせ、`ai_usage_quota_exhausted`をwarn、`ai_usage_limit_exceeded`をinfoで記録する。

Webの取り込みAPIは同じ判定を既存の429 `ai_usage_limit_exceeded`へ写し、プランでレスポンスを分けない。Shortcutと違い、画面側にはプラン情報があり、reasonを分けても伝えられる文言は増えない。
