# タグを利用者ごとの語彙として持つ

取り込みは確認を挟まずにRecipeを保存する（ADR 0019）。保存が増えるほど棚は追加日で並ぶだけになり、「主菜を探す」「取り込んだまま手を付けていないRecipeを片付ける」ができない。Recipeにタグを付け、一覧を絞り込めるようにする。

## RecipeContentの外に、利用者ごとの語彙として持つ

タグは、利用者ごとの語彙である`tags`と、Recipeへの付与である`recipe_tags`の2表で持つ。RecipeContentにもSourceにも含めない。

- 同じタグかどうかは`normalized_name`で決め、利用者の中で一意にする。これは、全角半角・空白・先頭の`#`を揃えた表示名を小文字にしたものである。表示名は最初に作ったときの綴りを残す。
- 付いているRecipeが0件になってもタグは消さない。名前の変更・統合・削除は語彙に対する操作として行う。
- 既存のタグと同じ名前に変えようとしたら`tag_name_conflict`を返し、画面でそのタグへの統合を確かめる。統合を別の機能として置かない。
- 付与は、Recipeとタグのどちらを消してもcascadeで消える。

## 付けるのは詳細画面だけにする

URL・テキストの取り込み、iOS Shortcut、手入力のどの経路でも、保存したRecipeは詳細画面で開く。そのためタグは詳細画面のシートで付け外しし、編集フォームには置かず、付ける経路を1つにする。付け外しは本文の編集ではないので`updatedAt`を変えない。ロック中のRecipeには付け外しできない。

組の置き換えは、`PUT /api/recipes/:recipeId/tags`に名前の配列を送る。名前で送るので新しいタグの作成も同じ要求で済み、同じ内容を送り直しても結果は変わらない。タグの作成、外したタグの付与の削除、付与の追加は、ADR 0001に従い単一SQLで行う。

## 一覧はANDで絞り込み、検索は読み取り時にタグ名も照合する

- 複数のタグを選ぶと、すべてが付いたRecipeに絞る。検索語もANDなので、条件はすべて重なるものとして揃える。「タグなし」は他のタグと同時には使わない。
- 検索語は語ごとに、`searchText`かタグ名のどちらかに当たればよい。タグ名は`searchText`に書き込まない。書き込むと、名前を変えるたびに付いている全Recipeを書き換えることになる。
- Freeで開けておくRecipeは全体のうち新しく保存した5件で決まる（ADR 0020）。タグで絞っても、どちらの並び順でも、ロック中のRecipeは一続きのままになる。
- 一覧のcursorに絞り込み条件は含めない。検索語と同じ扱いで、画面は条件ごとに別のクエリとして引き直す。
- プランによってタグの機能を制限しない。Freeは5件までしか保存できないので、制限しても分岐が増えるだけになる。

取り込み時にAIでタグを付けるかどうかは、この語彙から選ばせる前提で別に決める。

## 採らなかった案

- **`recipes.tags`を`text[]`で持つ**：書き込みは既存の単一SQLに列を足すだけで済み、この件数規模なら性能差もない。ただ、表示名と同一性の判定キーを分けられず、0件のタグを語彙として残せない。名前の変更や統合も、付いている全Recipeの配列の書き換えと重複除去になる。
- **RecipeContent（jsonb）に入れる**：編集フォームの丸ごと置き換えやAIの出力と混ざり、名前を変えるとcontentを書き換えることになる。
- **1つだけ選ぶカテゴリや固定のカテゴリ**：「鶏肉・作り置き・お弁当」のような重なりを表せず、分け方も人によって違う。語彙が空の利用者には、選ぶまで作らない定番候補を出して始めやすくする。
- **ORでの絞り込み**：使う場面が少なく、ANDと混ぜると画面で説明できない。
- **編集フォームにタグ欄を置く**：付ける経路が2つになる。どの経路でも保存後は詳細画面を開くので要らない。
