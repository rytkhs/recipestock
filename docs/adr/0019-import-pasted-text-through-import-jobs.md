# 貼り付けたテキストもImport Jobとして取り込む

URL取り込みと手入力に加え、レシピの文章を貼り付けてAIで整形し、Recipeとして保存できるようにする。LINEで届いたレシピ、メモアプリの自作メモ、取得できないページの本文、テキスト認識でコピーした本の文章などを取り込み対象にする。

テキスト取り込みはURL取り込みと同じImport Jobに`kind: "text"`として載せ、Cloudflare Queueで非同期に処理する。送信後は`/recipes`へ戻って取り込み状況パネルで結果を知らせ、成功したらRecipeを自動で保存する。AIの結果を手入力フォームへ流し込み、ユーザーが保存を押す同期APIは採らない。AIを待つ間にPWAがバックグラウンドへ回ると結果が失われて利用回数だけが減り、投稿時の上限判定(ADR 0010)と保存上限を含む原子的な保存を、別の経路で作り直すことになるためである。画像取り込みの設計地図(#105)がImport Jobに載せると決めたのと同じく、既存の非同期処理と投稿時の判定をそのまま使える。

## 投稿時の判定を共有し、同じ原文はhashで判定する

投稿時の判定は、active Jobの再利用、保存上限、AI上限の順に単一SQLで行う既存の構造(ADR 0001、ADR 0010)をURLと共有する。入力の種類で変わるのは、同じImport Jobとみなす条件だけである。URLは正規化URLを、テキストは前後の空白を除いた原文のSHA-256を`source_text_digest`に持ち、`queued`と`running`のJobに限った部分一意インデックスで一件へ収束させる。連打や再送には、URLと同じく既存のactive Jobを返す。

原文は前後の空白を除いて5,000文字までとする。AIは原文の言い回しをほぼそのまま写すので、出力は入力とほぼ同じ長さになり、推論トークンと出力の上限を共有するモデルでは入力より先に出力が詰まる。上限は入力のコンテキスト長ではなく出力の予算から決め、黙って切り詰めずに入力画面で止める。本文をJSONとして読む前にも、route側で大きさを抑える。

## 出典は付けない

テキスト取り込みのRecipeは`sourceUrl`も`sourceName`も持たない。手入力と同じ扱いであり、出典名を後から編集できるようにする場合は、手入力を含めた別の決定とする。

## AIへの入力と失敗の扱い

AIにはテキスト用のpromptProfileで原文だけを渡す。本文にタイトルがなければAIに料理名を付けさせ、ほかの項目は推測させない。AIがタイトルを返さなかったときは、URL取り込みのページmetadataに当たるものとして原文の最初の行を使う。複数のレシピを含む場合は主な一つだけを取り込み、1 Import Job = 1 Recipeを保つ。

材料も手順も読み取れなければ`extraction_failed`で失敗させる。空のRecipeを保存しても使い道がなく、原文を直して送り直してもらうほうがよい。AI利用回数は既存の規則どおりAIを呼んだ時点で消費し、この失敗でも戻さない。

入口はアプリ内の「テキストから」画面だけとする。Androidの共有やiOS ShortcutでURLが見つからない入力をテキスト取り込みへ回す経路は、この決定に含めない。
