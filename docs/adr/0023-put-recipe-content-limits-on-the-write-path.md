# レシピ本文の上限を書き込み経路に置く

画像には1枚5MB、レシピ画像20枚、手順ごと10枚、1レシピ合計100枚の上限があるが、本文には長さも件数も上限がなかった。`title`も`note`も手順の文も材料名も`z.string()`のままで、手順や材料の個数にも制限がない。`/api/recipes`にはリクエストの大きさの上限もないため、ログインさえしていれば1つのRecipeの`content`に数MBのJSONを保存できる。保存した本文は`searchText`に入って以降すべての検索で`ILIKE`の走査対象になり、一覧と詳細のレスポンスも同じだけ膨らむ。

そこで本文の長さと件数に上限を決める。基準はAIの出力予算(8,192トークン)で、取り込みで作れるRecipeがすでにその大きさに収まっていることを目安にする。レシピ名200文字、できあがり量100文字、メモ5,000文字、手順1つ2,000文字、材料名200文字、分量100文字、グループ名100文字、手順100個、材料のグループ50個、グループごとの材料100個、出典名200文字とする。手入力でこれを超えるレシピは想定しない。

出典URLだけは基準が違う。`normalized_source_url`はbtree indexに載っていて、btreeは1エントリが約2,704バイトまでしか入らない。それより大きい上限を置くと、schemaが通した値をDBが拒む。上限はWeb上の事実上の限界である2,048文字とし、schemaが通した出典URLは必ず保存できるようにする。

## 上限は書き込み経路にだけ置く

上限は`recipeDraftContentSchema`と保存要求のschemaに置き、保存済みの本文を表す`recipeContentSchema`には置かない。保存済みの本文はDBから読むたびに`recipeContentSchema.parse`を通るので、ここに上限を足すと、上限より大きい既存のRecipeが読めなくなる。上限を後から縮めるときも同じことが起きる。読み取りは保存されている値をそのまま返し、大きさの判断は書き込むときに一度だけ行う。

同じ理由で、出典の上限も保存要求のschemaにだけ置く。詳細のレスポンスが通る`recipeSourceSchema`には置かない。

## 取り込みは切り詰め、手入力は止める

手入力は入力画面で止める。利用者が長さを選べるので、黙って切り詰めるより、保存できない理由を伝えて直してもらうほうがよい。入力欄には`maxLength`を付けて上限を超える入力自体を防ぎ、それでも残った検証エラーは保存エラーと同じ帯に出す。

取り込みは切り詰める。ページやAIの出力の長さは利用者が選べず、1文字超えただけで取り込み全体を失敗させると、AI利用回数だけを消費して何も残らない。`trimRecipeDraftContent`が画像の枚数と本文の長さ・件数を同じ場所でまとめて末尾から落とし、保存できる形にしてから返す。出典名はページのmetadata由来で長さを選べないため、保存要求のschemaではなく`normalizeRecipeSource`で切り詰める。

出典URLは切り詰められない。末尾を落とせば別のページを指すURLになり、出典として意味をなさなくなる。代わりに`assertImportUrlAllowed`で長さを確かめ、上限を超えるURLは追いかけない。この関数は入口のURLだけでなくリダイレクト先にも呼ばれるので、利用者が選べないリダイレクト後のURLもここで止まる。fetchより前なので、AI利用回数を消費してから失敗することもない。

## リクエストの大きさで先に止める

`/api/recipes`に1MBのリクエスト上限を置く。画像はR2へ直接PUTするので、本文のJSONが大きくなる理由がない。本文の上限だけでも保存は防げるが、それは数MBのJSONを読み込んでZodで検証した後の話になる。テキスト取り込み(ADR 0019)が本文をJSONとして読む前に大きさを抑えているのと同じ形にする。

## 検索の入力も条件の数で抑える

検索クエリは200文字までとし、語は8語までにする。語はそれぞれ`searchText`への`ILIKE`とタグ名への`EXISTS`になるので、語数がそのまま条件の数になる。あわせて検索語の`%`と`_`をエスケープする。エスケープしないと`%`だけの検索語が全件に当たり、`_`が任意の1文字として照合される。

## 採らなかった案

- **保存済みの本文にも同じ上限を置く**：書き込みと読み取りで同じschemaを使えるが、上限を足した時点で既存のRecipeが読めなくなる。上限を縮めるたびに移行が必要になる。
- **取り込みも上限超過で失敗させる**：扱いは一つで済むが、AI利用回数を消費した後に何も残らない失敗が増える。長さは利用者が選べない。
- **リクエストの上限だけを置く**：入口は塞げるが、1MB以内でも1つの手順に90万文字を入れられる。検索と一覧が重くなる原因は総量ではなく1項目の大きさでも起きる。
