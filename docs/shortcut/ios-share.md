# iOS共有Shortcut

`VITE_IOS_SHARE_SHORTCUT_URL`から配布するShortcutの定義と、対応するAPI契約の記録。iCloudリンクの実体はレビューもdiffも取れないため、API契約を変更するときは必ずこの文書と突き合わせる。

配布後のShortcutは更新できない。判断ロジックはサーバーに置き、Shortcutは受け取った文字列を表示するだけにする（ADR 0004）。

## 現行バージョン

`X-Shortcut-Version: 1`

## アクション列

1. **共有シートから受け取る** — 受け付ける型はURL、テキスト、Safari Webページ、記事
2. **テキスト** — 手順1の入力をテキストへ変換する
3. **URLの内容を取得**
   - URL: `https://<app-host>/api/shortcut/import-jobs`
   - メソッド: `POST`
   - ヘッダ: `Authorization: Bearer <連携キー>` / `X-Shortcut-Version: 1`
   - 本文: JSON、`input` = 手順2の結果
4. **通知を表示** — タイトル `notice.title`、本文 `notice.body`
5. **もし** `notice.openUrl` が `https://` を含む **なら** — **URLを開く** `notice.openUrl`

連携キーは、Shortcut追加時のインポート質問でユーザーが貼り付ける。質問文は「KitchenCatでコピーした連携キーを貼り付けてください」とし、設定画面の「共有から取り込む」（`/settings/share`）の言葉と合わせる。判断ロジックはゼロ、分岐は手順5の1つだけである。

画面では「連携トークン」と呼ばない。「トークン」は利用者に伝わらず、インポート質問はアプリの外に出るので説明を添えられない。「キー」は人に見せない・無効にできるという性質を伝え、ログインの「確認コード」とも紛れない。APIとDBでは従来どおりtoken/credentialと呼ぶ。

`notice.body`は常に存在し、2行目を出さないreasonでは空文字になる。手順4はbodyの有無を分岐せず、空文字のときはタイトルだけの1行通知になる。

手順5に「値がある」を使わない。Shortcutsの「値がある」は空でないことの判定ではなく、辞書から取り出した値は空でも「値がある」側へ流れる。JSONの`null`が「値なし」「空文字」「文字列`null`」のどれになるかはAppleが仕様として公開しておらず、iOSの版で変わりうる。配布後のShortcutは更新できないため、この未定義の挙動に分岐を賭けない。`openUrl`は必ず絶対URLなので、`https://`を含むかどうかで判定すれば`null`がどう化けても必ず偽になる。

## API契約

### Request

```http
POST /api/shortcut/import-jobs
Authorization: Bearer rssc_...
X-Shortcut-Version: 1
Content-Type: application/json

{ "input": "この唐揚げ美味しそう https://www.instagram.com/p/xxxx/ #レシピ" }
```

`input`は共有入力をテキスト化したもので、1〜8192文字。URLの抽出はサーバーが行う。

連携キーは`rssc_`と乱数25文字（`[A-Za-z0-9_-]`）の計30文字で、150bitである。DBにはSHA-256のhashだけを保存し、末尾4文字を`tokenSuffix`として平文で持ち、設定画面の連携キーの一覧に出す。suffixは平文で公開する分だけ実効エントロピーを削るため、長くしない。認証はhash照合だけで行い長さや文字種を検査しないので、旧形式の発行済みトークンもそのまま有効である。

### Response

routeが把握している結果はすべて`200`で返す。非2xxはrouteが把握していない例外だけであり、Shortcutはそれを表示できない。

```json
{
  "outcome": "accepted",
  "reason": "created",
  "notice": {
    "title": "取り込みを開始しました",
    "body": "",
    "openUrl": null
  }
}
```

| `reason` | `outcome` | `body` | `openUrl` |
| --- | --- | --- | --- |
| `created` | `accepted` | 空文字 | なし |
| `existing_active_job` | `accepted` | 空文字 | なし |
| `setup_verified` | `accepted` | 空文字 | なし |
| `no_url_in_input` | `rejected` | 空文字 | なし |
| `invalid_url` | `rejected` | あり | なし |
| `malformed_request` | `rejected` | あり | `/settings/share?reason=malformed_request` |
| `recipe_limit_exceeded` | `rejected` | あり | `/settings/billing?upsell=recipe_limit&from=shortcut` |
| `ai_usage_limit_exceeded` | `rejected` | あり | `/settings/billing?upsell=ai_usage_limit&from=shortcut` |
| `ai_usage_quota_exhausted` | `rejected` | あり | なし |
| `rate_limit_exceeded` | `rejected` | 空文字 | なし |
| `temporarily_unavailable` | `rejected` | あり | なし |
| `missing_credential` | `rejected` | あり | `/settings/share?reason=missing_credential` |
| `unusable_credential` | `rejected` | あり | `/settings/share?reason=unusable_credential` |

`openUrl`のキーは常に存在し、遷移先がないreasonでは`null`になる。`body`と違い空文字は返さない。設定の確認への応答は、どのreasonでも`openUrl`を返さない（「設定の確認」）。

`/settings/share`へ送るreasonには`reason`を添え、開いた画面が、なぜ来たのかを伝えてから入れ直しの手順を出せるようにする。

バナーは一瞥されるだけの表示であり、`body`は次に取るべき行動があるreasonにだけ置く。`title`の言い換えにしかならない2行目は持たせない。

AI月次上限はプランでreasonを分ける。保存上限がfreeの投稿を先に止めAIを消費させないため、freeが`ai_usage_limit_exceeded`に達するのは例外的であり、実際に到達するのは主にProである。すでに払っているProへ「Proにすると」と案内しても意味がないので、`ai_usage_quota_exhausted`はopenUrlを持たせずリセット時期だけを伝える。リセットはJST月初固定なので「毎月1日」は常に真であり、日付を補間する必要はない。

上限値は運用中にenvで変えられるため、`body`に具体的な回数を書かず、文言の一覧を固定のまま保つ。Freeの回数は、遷移先のプランのページが今の値から出す。利用者向けの文言では「AI取り込み」の上限と呼ぶ。

表示文言は`apps/api/src/ios-share-notices.ts`が唯一の出所であり、Shortcutは文言を組み立てない。`reason`はHTTPステータスに代わる監視の軸で、routeは結果ごとに`ios_share_shortcut_import_submitted`を出力する。`malformed_request`、`missing_credential`、`unusable_credential`、`rate_limit_exceeded`、`temporarily_unavailable`、`ai_usage_quota_exhausted`はwarn、それ以外はinfo。freeのAI上限到達はコンバージョン機会であり通常の利用結果だが、proの枠切れは容量または濫用の兆候であるため別のlevelで扱う。

`malformed_request`はrequest bodyが契約に合わない場合、`no_url_in_input`は`input`にURLが含まれない場合であり、両者を混ぜない。前者はクライアントの契約違反、後者はユーザーの通常の操作結果である。

`rate_limit_exceeded`は2つの安全弁から返る。`credentialId`単位の毎分10回と、認証へ到達する前にclient IP単位で引く毎分60回である。後者は、無効なtokenを送り続けるrequestがtoken hash照合のDBアクセスを無制限に起こすのを防ぐ。keyは`cf-connecting-ip`とし、Cloudflareの背後では常に付与されるため、欠落するlocal devやtestでは共通のkeyで数える。IPは監視ログへ残さない。responseはどちらの安全弁でも同じ`reason`と同じnoticeであり、切り分けはログの`rateLimitScope`（`client`または`credential`）で行う。

認証の失敗は、連携キーの形をしたものが届いたかで2つの`reason`に分ける。届いていなければ`missing_credential`（キーが入っていない）、届いていれば`unusable_credential`（使えなくなった）である。どちらも利用者がすることは入れ直しで変わらないが、通知と連携し直しの画面で起きたことをそのまま伝えるために分ける。さらに細かい内訳は、ログの`authFailure`で連携の設定のどこで詰まったかを分ける。

| `reason` | `authFailure` | 条件 | 主な原因 |
| --- | --- | --- | --- |
| `missing_credential` | `missing_token` | Bearerがない、または空 | インポート質問でキーを貼らずに追加した |
| `missing_credential` | `malformed_token` | 照合できず、今の連携キーの形でもない | 別のものを貼った（コピーに失敗した、途中で別のものをコピーした） |
| `unusable_credential` | `unknown_token` | 今の形だが照合できない | 別の環境で発行したキー、手で打ち間違えたキー |
| `unusable_credential` | `revoked_token` | 解除済みのキー | 解除したキーのショートカットを使い続けている。`credentialId`と`userId`を添える |

`unknown_token`は、一度も有効でなかったキーなので「使えなくなった」とは厳密には言えない。それでも`revoked_token`と分けない。利用者のもとで起きることはまれで、responseで分けると、その形のキーがかつて存在したかを教えることになる。画面の文言は「解除されたなどで」とし、解除したと言い切らない。

形の判定は伝え分けとログのためだけに使い、認証はhash照合だけで行う。

### 設定の確認

設定画面の③は、設定画面そのもの（`/settings/share`）を`navigator.share`で共有メニューに渡し、「KitchenCat」を選んでもらう。共有の入力の最初のURLが、originが`APP_ORIGIN`と同じで、pathが`/settings/share`と完全一致したときだけ、取り込みではなく設定の確認として扱う。queryとhashは見ない。自分のoriginの別のpathや、別のoriginの同じpathは、ふつうの取り込みになる。pathは`packages/shared`の`IOS_SHARE_SETUP_CHECK_PATH`で、webとapiが同じ値を使う。

専用のpathにはしない。Safariで設定している人が、③のボタンではなくSafariの共有ボタンを押すと、送られるのは開いている`/settings/share`である。どちらのボタンで送っても、確かめられること（この端末のショートカットが、このアカウントのキーを持ち、接続の許可も済んで届くか）は同じで、Safariの共有ボタンはあとでレシピのページを送るときの道そのものでもある。専用のpathにすると、この場合はふつうの取り込みになり、上限に当たれば課金画面がSafariで開き、当たらなければ設定画面のImport Jobができる。

確認は、認証を通ったら`setup_verified`（「連携できました」）を返す。Import Jobは作らず、保存上限やAI取り込みの上限にも当たらない。`outcome`は受け付けたか断ったかの2つに閉じておき、確認が通ったのは断ったのではないので`accepted`とする。`outcome`で動きが変わるものはない（ショートカットは`notice`と`openUrl`だけを使い、ログのlevelは`reason`で決め、計測は`import_jobs`を数える）ので、値を足す理由がない。

routeの順:

1. client IP単位の上限 → `rate_limit_exceeded`
2. 本文が64KBを超える → `malformed_request`（超えた分は読まない）
3. 本文を読む（ここでは返さない）
4. 本文が契約に合い、最初のURLが確認用のURLか → 確認かどうか
5. Bearerがない → `missing_credential`
6. 認証（ここで`first_used_at`と`last_used_at`を書く） → `unusable_credential` / `missing_credential`
7. 確認なら → `setup_verified`
8. `credentialId`単位の上限 → `rate_limit_exceeded`
9. 本文が契約に合わない → `malformed_request`
10. `no_url_in_input`、取り込みの作成

`setup_verified`は、認証の直後、`credentialId`単位の上限より前に返す。上限のあとに置くと、上限に当たった確認では、通知は「少し時間をおいてください」なのに、認証で記録した時刻を見た画面は「連携できました」になる。`credentialId`単位の上限が抑えているのは取り込みの作成だけで、確認は取り込みを作らない。DBへの書き込みは、認証の前のclient IP単位の上限で抑える。

確認への応答は、どの`reason`でも`openUrl`を返さない。確認は設定画面の上で起きるので戻る先にはもういて、Safariで開くと、ホーム画面アプリで設定している人がログインもlocalStorageも別の入れ物へ移される（#152）。そのために、認証の失敗を返す前に本文を読む。認証できないrequestの本文も読むことになるが、回数はclient IP単位の上限で、1回の大きさは読む前の64KBの上限で抑える。大きさは上限のあとで見る。`Content-Length`がないと大きさは本文を読んで数えるので、先に見ると、上限に当たった送信元にも本文を読ませることになる。64KBは、上限文字数の入力がJSONのエスケープで膨らんでも収まる大きさである。

確認からの認証の失敗は、`reason`も文言も変えず、`openUrl`だけを返さない。`reason`は起きたこと（キーが入っていない、使えない）を表し、確認かどうかは別の軸である。確認と分かった応答のログには`setupCheck: true`を足す。

ショートカットは受け取った入力を送り、返った`notice`を出すだけなので、確認のために`X-Shortcut-Version`を上げる必要も再配布も要らない（ADR 0004）。

## 連携キーの利用の記録

認証を通したrequestは、同じSQLで連携キーの`first_used_at`と`last_used_at`を記録する。取り込みを受け付けたかどうかは問わず、設定の確認も同じく記録する。`no_url_in_input`や上限で止まったrequestでも、キーの貼り付けと接続の許可は済んでいるので、連携の設定は済んだとみなす。`first_used_at`は上書きしない。解除済みのキーは記録しない。

キーは端末を表さない。ショートカットはiCloudで同じApple IDの端末へ同期されうるので、1本のキーを複数の端末で使うことも、発行し直しや連携し直しで1台に複数のキーが残ることもある。キーの名前（iPhone、iPad）は発行した場所でしかないので、画面は台数を数えず、`lastUsedAt`をキーごとの最後に使った日として出す。使われなくなったキーの片付けは #224 で扱う。

ショートカットから作ったImport Jobは、作ったときの連携キーを`import_jobs.shortcut_credential_id`に残す。同じURLのactive Jobへ合流したときは、作った側の値を書き換えない。アプリから作ったJobはnullである。

## 設定画面の決め方

設定画面（`apps/web/src/features/ios-share/`）は、どこまで進んだかを端末に覚えず、連携キーの一覧だけから出す画面を決める。ホーム画面から開いたアプリとSafariはlocalStorageもログインも別で、連携し直しの`openUrl`はSafariで開くため、端末に覚えた進み具合は入れ物ごとに食い違う。

アプリからは、端末にショートカットが入っているか、どのキーが入っているかが見えない。見えるのは連携キーの一覧と、設定をどこから始めたかだけである。画面の各部分は、設定の始まり方（表1）と設定の中の段階（表2）から決め、部分ごとに別の条件を組み立てない。設定の外の画面は表3に置く。アプリから見えない端末側の状態と環境の違いは、どこで扱うかを表4と表5に書く。始まり方、段階、画面の部分を足すときは、先にこの表を埋める。表1から表3を変えたら、UIギャラリー（`apps/web/src/gallery/ios-share.tsx`）の行と列も合わせる。

### 表1 設定の始まり方

使ったキー（`firstUsedAt`がある）が1本でもあれば連携済みとし、設定をしていなければ連携の管理を出す。未連携なら、いつも設定の途中にいる。

| 始まり方 | 導入 | ショートカットがもうありうるか | 続きから出すキー |
| --- | --- | --- | --- |
| 未連携で開いた（使われていないキーなし） | 初回の案内 | ない | なし |
| 未連携で開いた（使われていないキーあり） | 初回の案内 | ありうる | いちばん新しい使われていないキー |
| 連携の管理を出している間に未連携になった（最後の使ったキーを解除した） | 初回の案内 | ある | 使われていないキーがあれば、いちばん新しいもの |
| 連携し直しに来た（`?reason=`） | 理由のお知らせ | ある | なし |
| 連携の管理で「この端末でショートカットを追加する」 | なし | ありうる（iCloudで同期されている） | なし |
| 連携の管理の「うまくいかないとき」で「最初からやり直す」 | なし | ある | なし |
| 設定の途中の「うまくいかないとき」で「最初からやり直す」 | 元の設定と同じ | ある（やり直しを案内するのは、追加したあとのつまずきだけ） | なし |

- 始めたときの一覧で、この表の値と完了の基準を決め、その設定の間は変えない。この画面で発行したキーが一覧に入っても、続きのキーとは取り違えない。
- 完了の基準は次の2つで、どちらかを満たせば完了にする。
  - 始めた時点で使われていなかったキー（その後に発行したキーを含む）のどれかに`firstUsedAt`が入る。発行し直す前のキーや、Safariで発行したキーで共有が届いても完了になる。新しいキーで③から確かめたときも、確認のrequestで`firstUsedAt`が入るので、ふつうはこちらで完了になる。
  - ③を押してから、どれかのキーの`lastUsedAt`が変わる（押したときになかったキーなら、`lastUsedAt`が入る）。押すたびに、キャッシュにある一覧からキーごとの`lastUsedAt`を覚え直し、発行し直したら捨てる。前のキー（使用済み）が入ったショートカットで確かめても、通知の「連携できました」と画面がそろう。連携の管理から「この端末でショートカットを追加する」とき、iCloudの同期や置き換えずに追加したことで前のショートカットが残り、それを選ぶと起きる。
- 「連携済み」は`firstUsedAt`で決まる。③を押さずにほかのアプリから共有した人は、アカウントがもう連携済みになっているので、`firstUsedAt`の基準を残し、通知・誘い・開き直したときの画面と食い違わないようにする。
- ショートカットがもうありうる（「ある」を含む）設定では、②で、同じ名前のショートカットがあると聞かれたら置き換えるよう添える。ない設定では添えない。
- 未連携で開いた人には、前にキーをすべて解除した人も含まれ、ショートカットが残っていることがある。見分けられないので、iOSの確認に任せる。
- 連携済みなら「やめる」を出し、連携の管理へ戻れるようにする。未連携では出さない。
- ②の見出しは、連携し直しでは「ショートカットを入れ直す」、それ以外は「ショートカットを追加」。

### 表2 設定の中の段階

| 段階 | ① | ② | ③ |
| --- | --- | --- | --- |
| キーなし | 「キーをコピー」。発行できなかったときは知らせる | 押せない | 手順と図。押せない |
| 発行中 | 押せない | 押せない | 手順と図。押せない |
| 発行してコピーできた | 済み。「もう一度コピー」 | 押せる | 手順と図。押せない |
| 発行したがコピーできなかった | 済み。キーを選んでコピーできるように出す | 押せる | 手順と図。押せない |
| 続きのキーがあり、この画面では発行していない | 済み。発行した端末・日・末尾と「キーを発行し直す」 | 控えめに押せる。まだ追加していなければ追加するよう伝える | 押せる（③の状態） |
| ②を開いた | 変えない | 済み。「もう一度開く」 | 押せる（③の状態） |

- ②は、キーを持つまで押せない。続きのキーがある段階では、もう追加したかどうか分からず、キーがまだクリップボードに残っていることもあるので押せる。
- ③は、②を開くか続きのキーがあるまで押せない。それまでに確かめても、ショートカットがないか前のキーのままなので意味がない。押せないときも、②と同じく押せないボタンとして出す。
- 発行し直したら、②を開いたことと③の結果を忘れる。新しいキーは、ショートカットに貼り直すまで使われない。
- ②を開いたあとに、キーを貼らなかったときの案内は出さない。「うまくいかないとき」と③の「まだ確かめられていない」に任せる。
- ③を押せる間は、一覧を定期的に読み直す。ボタンを押さずにほかのアプリから共有する人もいる。アプリへ戻ったときにも読み直す。
- どの段階でも、完了の基準を満たしたら「連携できました」を出す。
- 一度読めた一覧の読み直しに失敗しても、段階を変えない。コピーできなかったキーも消さない。

#### ③の状態

③は「この画面をKitchenCatへ共有する」手順で、ボタンは共有メニューを開く。共有メニューにはこの画面のURLだけを渡す（textを足すと`input`に余計なものが入る）。共有メニューはユーザー操作の中でしか開けないので、タップの処理の中で、awaitを挟まずに開く。

| 状態 | いつ | 出すもの | ボタン |
| --- | --- | --- | --- |
| 押せない | ②の前（続きのキーもない） | 手順と図 | 押せない |
| 押せる | ②を開いた、または続きのキーがある | 手順と図 | 押せる |
| 共有中 | 押してから、共有メニューの結果が返るまで | （共有メニューが前に出ている） | 押せない |
| 確かめている | resolveしてから最長5秒 | 「確かめています」 | 押せない |
| まだ確かめられていない | resolveして5秒たっても進まない、または`AbortError`（待たない） | 見つからないときの案内と、選んでも変わらないときの直し方、「最初からやり直す」 | 押せる |
| 開けなかった | `AbortError`以外のエラー、または`navigator.share`がない | 「共有メニューを開けませんでした。」 | 押せる |

- どの状態でも、完了の基準を満たしたら「連携できました」を出す。「まだ確かめられていない」を出したあとに遅れて届いても、完了になる。共有メニューの結果が返らないまま残っても、完了は一覧の読み直しだけで分かる。
- resolveしたら、すぐ一覧を読み直す。5秒は届くまでの揺れの分である。③を押せる間は3秒ごとに一覧を読んでいるので、Neonは止まっていない。
- `AbortError`は「共有メニューを閉じた」だけではない。WebKitは、共有メニューのどの項目も完了を返さなかったとき、理由を区別せずに`AbortError`を返す（`Source/WebCore/page/Navigator.cpp`の`showShareData`、`Source/WebKit/UIProcess/Cocoa/WKShareSheet.mm`の`_didShareSuccessfully`）。何も選ばずに閉じたときのほか、「KitchenCat」を選んだが、ショートカットが完了しなかった（「許可しない」、通信の失敗、途中で止めた）ときも含みうる。逆にresolveも、ほかの項目（コピー、メッセージなど）が完了しただけのことがある。どちらも`lastUsedAt`が進んだかだけで判定し、案内は1つにまとめる。
- requestを送ったあとで止まれば、`AbortError`でも`lastUsedAt`は進んでいる。覚えた一覧は捨てず、すぐ読み直す。
- `AbortError`以外は、共有メニューが開く前に起きる。`NotAllowedError`は実装の誤り、`TypeError`は渡したものが共有できないときで、URLは固定なので起きない。`navigator.share`がないときは、呼ぶ前に分けて「開けなかった」にする。`InvalidStateError`は前の共有の結果が返っていないときである。共有中は押せないので、起きるのは、結果が返らないまま、最初からやり直すか、発行し直して②を開き直してから押したときだけである。
- 「届きませんでした」とは言わない。キーが入っていない・使えないときはrequestが届いていて、通知も「連携キーが入っていません」などと出る。「まだ」なら、遅れて届いて完了に変わることとも、ほかのアカウントのキーで通知だけ「連携できました」になるまれな場合とも矛盾しない。

#### 残る食い違い

- Safariの共有ボタンで確かめたときは、③のボタンを押していないので、比べる元がない。新しいキーなら`firstUsedAt`の基準で完了になるが、前のキーが入ったショートカットだと、通知は「連携できました」なのに、画面は③のままになる。専用のpathにしても、この場合はふつうの取り込みになるだけなので、悪くはならない。
- ほかのアカウントのキーが入っていると、通知は「連携できました」なのに、画面は「まだ確かめられていません」になる（「確認IDを付けない」）。
- `lastUsedAt`は、③を押してから、押し直すか、発行し直すか、最初からやり直すまで比べ続ける。遅れて届いたものも完了にするためで、比べる間は区切らない。この間にほかの端末のショートカットで共有すると、この端末からは届いていなくても、画面は「連携できました」になる。
- 比べる元は押した時点のキャッシュの一覧なので、最後の読み直しから③を押すまで（③を押せる間は3秒ごとに読み直すので数秒）に、ほかの端末で共有したものも同じく完了になる。押してから読み直すと共有メニューを開けなくなり（タップの処理の中で、awaitを挟まずに開く）、並べて読んだ一覧を元にすると、この端末からの確認が先に記録されたときに完了を取りこぼすので、キャッシュの一覧を使う。

## 設定への入口

設定の外からも設定へ誘う（`apps/web/src/features/ios-share/use-shortcut-setup-offer.ts`）。誘うのはiPhoneとiPadで、アカウントにまだ使ったキーが1本もないときだけ。ショートカットはiCloudで同期されうるので、端末ごとには判定しない。

| 場所 | 誘うときに出すもの |
| --- | --- |
| 空の一覧 | 「URLを貼って取り込む」と「共有ボタンから送る」を同じ重さで並べる。誘わないときは「URLから取り込む」だけ |
| レシピ追加のシートとメニュー | 区切って最後に「共有から取り込む」 |
| レシピがある一覧（絞り込み中を除く） | 「次は、共有ボタンから」。連携するか「今はしない」を押すまで出す |

- 連携キーの一覧を読めるまでは誘わない。空の一覧には、その間どちらの始め方も出さない。URLだけの始め方から2択へ差し替えず、設定を済ませた人に一瞬だけ見せることもしない。
- 連携キーの一覧は、レシピの一覧を開くときにrouterのloaderがレシピの一覧と並べて取り始める。画面が出てから取り始めると、出した一覧の上に誘いが遅れて差し込まれる。
- 一度読めた一覧の読み直しに失敗しても、誘うかどうかを変えない。
- 読めなかったときは誘わず、空の一覧には「URLから取り込む」だけを出す。画面を出してから一度そう決めたら、読み直している間も変えない。
- 共有はアプリの外で起きるので、連携するまではアプリへ戻るたびに一覧を読み直し、連携できたら誘いを消す。
- 項目の名前には端末名の札（`DeviceBadge`）を添える。「次は、共有ボタンから」は見出しが文なので添えない。
- 「今はしない」はlocalStorageに覚える。Safariとホーム画面から開いたアプリでは別々に覚え（表5）、アカウントでは分けない。

## 計測

設定の流れと共有からの利用は、上の列とログから、見たいときにSQLで数える。定期実行の監視は置かない（ADR 0010）。連携キーは発行し直すと同じ人に複数できるので、設定の完了は人単位で数える。

```sql
-- 人ごとの、設定を始めた日時・初めて使えた日時・使われていないキーの数
select user_id,
       min(created_at)    as started_at,
       min(first_used_at) as first_used_at,
       count(*) filter (where first_used_at is null and revoked_at is null) as unused_keys
from shortcut_credentials
group by user_id;

-- 共有から取り込んで保存できた人
select count(distinct user_id)
from import_jobs
where shortcut_credential_id is not null
  and status = 'succeeded';
```

設定の確認は取り込みを作らないので、`import_jobs`には現れない。確認が通った数は`reason`が`setup_verified`のログで、確認からの認証の失敗は`setupCheck`の付いた`missing_credential`と`unusable_credential`のログで数える。後者が多く、③の案内を見てもやり直せていないと分かったら、確認IDを足す（「確認IDを付けない」）。

発行してから使われるまでの間で、リクエストが届く失敗（キーを貼っていない、別のものを貼った）は`missing_credential`として数えられ、内訳は`authFailure`で分かる。ショートカットを追加していない、接続の確認で「許可しない」を選んだ、はリクエストが届かないので観測できず、使われていないキーとしてだけ現れる。

## 確認IDを付けない

共有するURLに確認ごとのIDを入れれば、ショートカットからのrequestで結果をサーバーに書き、失敗の中身も画面で出し分けられる。これは付けない。

- 押したのに通知と画面が食い違う場合は、`lastUsedAt`の比較で解ける。認証を通ったrequestは、そのキーの`lastUsedAt`を必ず更新する。ほかの端末からの共有と取り違えるのは、③を押す前の最後の読み直しのあと、この画面を開いたままほかの端末で共有したときだけである（「残る食い違い」）。どのキーが入っているかも分かる（#224）。
- 失敗の中身を出し分けても、利用者のすることは変わらない。キーが入っていない、使えないキーだった、「許可しない」を選んだ、のどれも、直し方は「ショートカットを削除して、キーのコピーからやり直す」である。ショートカットの通知を許可している人には、バナーが理由を伝える。

IDがないとできないのは、通知を切っている人にも理由を画面で伝える、押したのに届かなかった回数をSQLで数える、ほかのアカウントのキーが入っていた、などのまれな場合を正確に扱う、の3つだけで、テーブル、endpoint 2本、未認証のrequestからの書き込みには見合わない。

IDは後から足せる。ショートカットは受け取ったURLをそのまま送るだけなので、変えるのはサーバーとアプリだけで、再配布は要らない。足すときの形:

- 置き場所はNeonのテーブルにする。書いた直後にアプリが読むのでWorkers KV（結果整合）は合わず、`shortcut_credentials`の列には認証を通ったキーの結果しか書けない。
- 行を作るのはアプリ（ログインしたセッション）だけにする。ショートカットからのrequestにできるのは、作ってあって結果のない行の更新（`where id = ? and resolved_at is null`）だけにし、`verified`は届いたキーがその行の`user_id`のものだったときだけ書く。
- IDは、タップの処理の中でアプリが`crypto.randomUUID()`で作り、行を作るPOSTと`navigator.share`を同じタップで始める。1回押すごとに1行にする。
- IDは確認用のURLのqueryに入れる。確認かどうかの判定はqueryを見ないので、そのまま足せる。
- 認証のSQLには混ぜない（ADR 0001）。確認の行の更新と`first_used_at`の記録は、同時に成り立っている必要がない。

```txt
shortcut_setup_checks
  id             text primary key   -- URLに入る乱数
  user_id        text not null
  created_at     timestamptz not null
  result         text               -- null（未着）/ verified / missing_credential / unusable_credential
  credential_id  text               -- verifiedのとき、届いたキー
  resolved_at    timestamptz
```

## 共有入力の実機確認

`受け取るもの`を`すべて`にした状態で、Safari（記事・通常ページ）、Instagram、YouTube、LINE、X、レシピアプリから共有したとき、`input`の先頭に現れる`https://`は常に共有対象のURLと一致した。記事本文が`input`へ入る事象は観測されていない。したがってサーバー側の抽出は先頭のURLを採用し、`input`の上限は8192文字とする。

画像・スクリーンショットを共有した場合、`input`にはファイル名が入る。URLを含まないため`no_url_in_input`となる。画像の共有取り込みは未対応である。

受け取る型やこの前提を変える場合は、同じ確認をやり直してから契約を決める。

## 分岐の実機確認

配布前に、`openUrl`が`null`のreason（`created`）と`openUrl`を持つreason（キーを貼らずに追加して`missing_credential`）の両方を実機で通し、前者で遷移も失敗も起きないこと、後者で遷移することを確認する。手順5はShortcut唯一の分岐であり、配布後は修正できない。

## 設定の手順の実機確認

設定画面（`apps/web/src/features/ios-share/`）は、アプリの外で起きることを図と文で先に見せる。次はテストでは確かめられないので、iPhoneのSafariとホーム画面から開いたアプリの両方で確かめ、画面の図と文言を実機に合わせる。

- 「キーをコピー」の1回のタップで、発行を待ってからでもクリップボードに書けること（`ClipboardItem`にPromiseを渡している）
- 「ショートカットを追加」から、iCloudのリンクがショートカットAppで開くこと
- 初回の共有で出る接続の確認の文言と選択肢、ほかに送信の確認が出るかどうか
- 同じ名前のショートカットを追加すると、iOSは置き換えるか追加するかを聞く。残りを確かめる: ボタンの表記、置き換えでもキーを聞かれるか、置き換えたショートカットで接続の確認をもう一度聞かれるか、追加を選んだときに並ぶ名前、同期先がどうなるか。②の置き換えの案内と「うまくいかないとき」の文言はこれで決まる
- ショートカットAppやSafariから戻ったとき、一覧の読み直しで「連携できました」に変わること
- キーを貼ったショートカットが、iCloud同期で同じApple IDのiPadやMacに入り、そのキーで共有が届くこと。届かなければ、連携の管理の「ほかの端末でも使うには」（`shortcut-sync-note.tsx`）を消す。届くなら、Macでも連携し直しの`?reason=`が開きうるので、Macの画面にも理由と、iPhoneで入れ直す案内を出す
- Safariとホーム画面から開いたアプリで、ログインとlocalStorageがそれぞれ別になっていること
- `openUrl`（Safariで開く）から、ログインしたあとに`?reason=`付きの同じ画面へ戻り、連携し直せること
- ③の`navigator.share`の結果がいつ返るか。WebKitは、共有メニューで選んだ項目が終わって共有メニューが閉じたときに返す。ショートカットの拡張が、実行を最後まで終えてから完了を返すかを、Safariとホーム画面アプリで確かめる。先に返るなら、5秒を延ばすか、判定のきっかけを変える
- ③で「KitchenCat」を選んだあと、「許可しない」、通信の失敗、途中で止めた、のそれぞれで、resolveになるか`AbortError`になるか
- ③の共有メニューの結果が返らないまま残り、そのあと`InvalidStateError`で開けなくなることがないか。起きるなら、読み込み直す案内を考える
- URLを共有したときの共有メニューの並びが、③の図と合っているか

## 変更時の手順

1. `apps/api/src/routes/ios-share.ts`と`apps/api/src/ios-share-notices.ts`を変更する
2. 文言や遷移先だけの変更であれば、Shortcutの再配布は不要
3. アクション列やrequestの形が変わる場合は`X-Shortcut-Version`を上げ、この文書を更新し、古い版へ更新を促す`notice`を返す経路を用意し、「分岐の実機確認」を行ってから配布する
